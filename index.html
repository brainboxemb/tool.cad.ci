Overview

tool.cad.ci

tool.cad.ci is the thin command-line interface for BrainboxEmb CAD CI.

The reusable implementation lives in lib.py.cad.ci. This repository owns argument parsing, terminal output, documentation/release plumbing and CLI-specific tests. It does not implement its own planner, execution engine, cache, build store, Pages or Git publication mechanics.

The tool pins lib.py.cad.ci 0.5.0 at exact commit 345794521fe162eb1908e1e8f38a6eabb02c8290.

Consumer layout

cad-ci.yml
shared/
cases/simple_case1/
  ci.yml
  build.py
  verify.py

Root cad-ci.yml:

schema: 1

defaults:
  timeout_seconds: 300

variables:
  BUILD_MODE: "verify"

items:
  - cases/*

Item ci.yml:

id: simple-case

watch:
  - cases/simple_case1/**
  - shared/**

steps:
  - id: build
    inputs:
      - cases/simple_case1/build.py
      - cases/simple_case1/input/**
      - shared/**
    run: [python, build.py]
    outputs: [generated]

  - id: verify
    inputs:
      - cases/simple_case1/verify.py
    run: [python, verify.py]
    outputs: [verify.json]

watch is coarse Git-selection input. Step inputs are SCons build dependencies. If a step omits inputs, it inherits the item watch paths.

Root variables are validated by the pinned library, injected into every consumer command and included in SCons target signatures. Repository variables override inherited caller values with the same name; CAD-CI-owned CAD_CI_* values remain authoritative.

Plan and run

cad-ci plan --repo . --base <base-sha> --head <head-sha>
cad-ci run  --repo . --base <base-sha> --head <head-sha>

cad-ci run --repo . --item simple-case
cad-ci run --repo . --item simple-case --step verify
cad-ci run --repo . --item simple-case --until verify
cad-ci run --repo . --item simple-case --from build

plan explains which top-level items are selected and which dependencies they have. It does not claim whether SCons considers a step dirty or current.

One run command makes one library run_repository() call. SCons owns prerequisite traversal, incremental decisions and CacheDir reuse.

Partial selectors are mutually exclusive:

  • --step forces that exact step after making prerequisites current;
  • --until requests the named step normally;
  • --from forces the named step and every following step.

Consumer output mirrors the item source path below build/. Public execution evidence lives below build/<item>/.cad-ci/; private SCons state/cache stays below .cache/cad-ci/.

Reusable GitHub Actions

Consumers do not need to copy the generic CAD-CI setup into their own workflows. Reference the released reusable workflow at the exact tool commit.

For a normal PR/push run, the consumer keeps only its event trigger, permissions and one reusable-workflow call:

name: CI

on:
  pull_request:
  push:
    branches: [main]

permissions:
  contents: read

jobs:
  cad-ci:
    uses: brainboxemb/tool.cad.ci/.github/workflows/reusable-ci.yml@<tool-commit>

reusable-ci.yml delegates to the generic run workflow from that same tool revision. The called workflow:

  • checks out the caller repository at its real source commit;
  • checks out tool.cad.ci at the same commit that contains the called workflow;
  • installs that exact tool/library stack;
  • performs exactly one cad-ci run;

Consumers such as Forge that need domain setup between selection and execution can use the lower-level pair: first call reusable-plan.yml, prepare their runtime image, then call reusable-run.yml with explicit source/base SHAs. Normal consumers use reusable-ci.yml and do not reproduce generic checkout/Python/tool-install/run setup locally. None of these workflows contains Forge/SolidCraft/CAD-domain item names.

The optional environment_json input supplies non-secret caller values to the inherited process environment. Stable repository expectations, such as a runtime/version selected by that repository, belong in root cad-ci.yml:variables. The pinned library applies those repository values after caller environment. Secrets remain normal GitHub Actions secrets/permissions.

When a downstream consumer job must publish or transform generated output, set upload_build: true. The run workflow uploads the complete materialized build/ tree, including hidden .cad-ci evidence, and returns its name as build_artifact_name. Private .cache/cad-ci SCons state is never part of that artifact.

Durable build output

Fetch the generated build branch:

cad-ci build fetch --repo . --out generated-build

Prepare a complete main baseline:

cad-ci build prepare-main \
  --repo . \
  --candidate-root build \
  --out output/main \
  --source-commit <sha>

Prepare a sparse PR overlay:

cad-ci build prepare-pr \
  --repo . \
  --candidate-root build \
  --out output/pr \
  --source-commit <sha> \
  --pull-request 12 \
  --items simple-case

A PR overlay contains only the selected top-level items. Runtime prerequisites that SCons made current are not automatically added to the sparse overlay.

Update selected main items with cad-ci build update-main. Resolve main plus an optional PR overlay with cad-ci build resolve.

Generated branches are published with cad-ci publish build and cad-ci publish pages. Publication uses normal pushes, checks source freshness and retries only generated-branch races.

Verification order

Generic execution behaviour is developed and tested in lib.py.cad.ci. The CLI is tested here against one exact released library revision. The complete released tool/library stack is then black-box tested in tool.cad.ci.test.

Only after that exact stack passes may Forge or CAD migrate to it.
